## 문제 1 — `IllegalArgumentException` 직접 throw

### 원인

`task`, `wiki` 도메인의 Service에서 리소스를 찾지 못할 때
공통 예외 클래스(`UserNotFoundException` 등) 대신 `IllegalArgumentException`을 직접 사용하고 있다.

```java
// task/application/TaskPostService.java — 현재 코드
.orElseThrow(() -> new IllegalArgumentException("게시글을 찾을 수 없습니다: " + id));

// task/application/TaskFolderService.java — 현재 코드
.orElseThrow(() -> new IllegalArgumentException("폴더를 찾을 수 없습니다: " + id));

// wiki/application/WikiPostService.java — 현재 코드
.orElseThrow(() -> new IllegalArgumentException("문서를 찾을 수 없습니다: " + id));

// wiki/application/WikiFolderService.java — 현재 코드
.orElseThrow(() -> new IllegalArgumentException("폴더를 찾을 수 없습니다: " + id));
```

### 문제점

- `IllegalArgumentException`은 400 Bad Request로 처리된다.
  - 리소스가 없는 상황은 **404 Not Found**가 맞다.
- 에러 코드가 `"INVALID_ARGUMENT"`로 내려간다.
  - 클라이언트 입장에서 "입력값이 잘못됐다"는 의미로 오해할 수 있다.
- 공통 예외 구조(`ErrorCode`, `GlobalExceptionHandler`)를 만들어뒀는데 활용하지 않고 있다.
- 도메인 언어(`TaskPostNotFoundException`)가 없어서 예외만 봐도 어느 도메인 문제인지 알 수 없다.

### 개선 방향

```java
// 1. ErrorCode에 리소스별 에러 코드 추가
TASK_POST_NOT_FOUND("TASK_POST_NOT_FOUND", "게시글을 찾을 수 없습니다", HttpStatus.NOT_FOUND),
TASK_FOLDER_NOT_FOUND("TASK_FOLDER_NOT_FOUND", "폴더를 찾을 수 없습니다", HttpStatus.NOT_FOUND),
WIKI_POST_NOT_FOUND("WIKI_POST_NOT_FOUND", "문서를 찾을 수 없습니다", HttpStatus.NOT_FOUND),
WIKI_FOLDER_NOT_FOUND("WIKI_FOLDER_NOT_FOUND", "폴더를 찾을 수 없습니다", HttpStatus.NOT_FOUND),

// 2. 공통 예외 클래스 추가 (UserNotFoundException과 동일한 패턴)
public class ResourceNotFoundException extends RuntimeException {
    private final ErrorCode errorCode;
    ...
}

// 3. Service에서 교체
.orElseThrow(() -> new ResourceNotFoundException(ErrorCode.TASK_POST_NOT_FOUND));
```

## 문제 2 — `getUserIdFromAuth()` 하드코딩

### 원인

`task`, `wiki` 도메인의 모든 Controller에 아래 코드가 존재한다.

```java
private Long getUserIdFromAuth(Authentication auth) {
    // TODO: JWT 토큰에서 userId 추출
    return 1L;  // ← 하드코딩
}
```

### 문제점

- 로그인한 사용자와 무관하게 항상 userId = 1번으로 데이터가 저장된다.
- 다른 도메인(`DevLogController`, `MemoController` 등)은 이미 JWT에서 userId를 정상 추출하고 있다.
  - 즉, 구현 방법이 프로젝트 내에 이미 있는데 `task`, `wiki`에만 적용이 안 된 상태다.
- 실제 사용자 기반의 권한 체크, 작성자 표시가 전혀 동작하지 않는다.

### 개선 방향

다른 도메인의 구현 패턴을 그대로 가져온다.

```java
// 적용할 패턴 (DevLogController, MemoController에서 이미 사용 중)
private Long getUserIdFromAuth(Authentication auth) {
    if (auth == null || !auth.isAuthenticated()) {
        throw new ResponseStatusException(HttpStatus.UNAUTHORIZED, "로그인이 필요합니다.");
    }
    User user = (User) auth.getPrincipal();
    return user.getId();
}
```

## 문제 3 — Controller가 도메인 객체를 직접 반환

### 원인

`task`, `wiki` Controller의 응답 타입이 도메인 객체 그대로다.

```java
// task/presentation/TaskPostController.java — 현재 코드
public ResponseEntity<TaskPost> getPost(@PathVariable Long id) {
    return ResponseEntity.ok(taskPostService.getPostWithBlocks(id));
}

public ResponseEntity<List<TaskPost>> getPostsByFolder(...) { ... }
```

### 문제점

- 도메인 객체의 내부 필드가 모두 클라이언트에 노출된다.
  - 예: `authorId`, `deletedAt` 등 클라이언트가 알 필요 없는 필드까지 응답에 포함
- 도메인 객체 구조 변경이 즉시 API 스펙 변경으로 이어진다.
  - 도메인 내부 변경이 외부 계약에 영향을 주면 안 된다는 DDD 원칙 위반
- 목록 응답과 상세 응답이 같은 타입(`TaskPost`)을 사용해 불필요한 필드가 섞인다.

### 개선 방향

```java
// 목록용
public class TaskPostSummary {
    private Long id;
    private String title;
    private String authorName;
    private LocalDateTime createdAt;
}

// 상세용
public class TaskPostDetail {
    private Long id;
    private String title;
    private String authorName;
    private List<TaskBlock> blocks;
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
}
```

## 문제 4 — `authorName`이 도메인 객체 안에 존재 (Bounded Context 침투)

### 원인

```java
// task/domain/TaskPost.java — 현재 코드
private String authorName;   // user 컨텍스트 데이터가 task 도메인 객체 안에 존재

// task/domain/TaskComment.java
private String authorName;

// wiki/domain/WikiPost.java
private String authorName;
```

### 문제점

- `task` 도메인 객체가 `user` 컨텍스트의 데이터(`authorName`)를 직접 보유한다.
- 도메인 객체의 책임이 "task 핵심 데이터 + user 조회 데이터"로 섞인다.
- `user`의 이름이 변경되거나 필드 구조가 바뀔 때 `task` 도메인 객체도 영향을 받는다.

### 개선 방향

- 도메인 객체는 `authorId`(ID 참조)만 보유한다.
- JOIN 결과(`authorName`)는 Response DTO(문제 3 해결 시 함께 처리)에서 담는다.
- 문제 3(Response DTO 분리)과 함께 해결하는 것이 효율적이다.

## 문제 5 — `WikiPost.tags` String 원시 타입 (Value Object 미적용)

### 원인

```java
// wiki/domain/WikiPost.java — 현재 코드
private String tags; // "컨벤션,TypeScript,필독" — 콤마 구분 문자열
```

### 문제점

- 태그 파싱/직렬화 로직이 Service에 흩어진다.
  ```java
  // WikiPostService.java
  String tags = request.getTags() != null ? String.join(",", request.getTags()) : "";
  ```
- 태그 유효성 검사(빈 문자열 제거, 중복 제거 등)가 도메인 외부에서만 가능하다.
- "태그" 개념이 단순 String인지, 콤마 구분 문자열인지 코드만 봐서는 알 수 없다.

### 개선 방향

```java
// Tags Value Object 도입
public class Tags {
    private final List<String> values;

    private Tags(List<String> values) {
        this.values = values.stream()
                .filter(s -> !s.isBlank())
                .distinct()
                .toList();
    }

    public static Tags from(String csv) {
        if (csv == null || csv.isBlank()) return new Tags(List.of());
        return new Tags(Arrays.asList(csv.split(",")));
    }

    public static Tags from(List<String> list) {
        return new Tags(list != null ? list : List.of());
    }

    public String toCsv() {
        return String.join(",", values);
    }

    public List<String> toList() {
        return Collections.unmodifiableList(values);
    }
}
```
