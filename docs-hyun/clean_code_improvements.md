# ✨ 프로젝트 클린 코드(Clean Code) 개선 포인트

현재 백엔드(DDD)와 프론트엔드(FSD) 아키텍처는 전반적으로 잘 구성되어 있으나, **클린 코드 관점(유지보수성, 단일 책임 원칙, 가독성)**에서 봤을 때 아래와 같은 요소들을 개선하면 더욱 훌륭한 프로젝트가 될 수 있습니다.

---

## 1. 프론트엔드 (`parantier-front`)

가장 시급하게 수정이 필요한 부분은 방대한 책임을 지고 있는 컴포넌트들입니다.

### 🚩 문제점 & 개선 방안

1. **거대 컴포넌트 분리 (God Component 해소)**
   * **현황:** `TasksPage.tsx` 파일이 약 900줄(30KB)에 달합니다. 하나의 파일에 사이드바 트리 구조 렌더링, 컨텍스트 메뉴(`FolderContextMenu`, `PostContextMenu`), 로컬 상태(14개 이상), API 호출, 인라인 수정 등이 모두 섞여 있습니다.
   * **개선:** FSD 원칙에 맞게 분리해야 합니다. `FolderContextMenu` 등은 `features` 하위의 독립된 파일로 빼내고, 사이드바 부분은 `Widget`으로 추출하여 `TasksPage`는 단순히 이러한 위젯들을 조합(Composition)하는 역할만 해야 합니다.

2. **비즈니스 로직과 UI 렌더링의 혼재**
   * **현황:** 검색 로직, 트리 빌딩, 폴더/문서 상태 관리 로직이 UI 렌더링 함수 내부에 인라인으로 들어가 있습니다.
   * **개선:** `useTaskTree`, `useTaskContextMenu` 와 같은 **커스텀 훅(Custom Hook)**으로 상태와 로직을 묶어서 컴포넌트 밖으로 빼내야 합니다.

3. **과도한 인라인 함수 지양**
   * **현황:** `<input onKeyDown={(e) => { ... 복잡한 조건문 ... }}>` 처럼 JSX 내부에 긴 로직이 인라인 함수로 작성되어 가독성을 해치고 불필요한 렌더링을 유발합니다.
   * **개선:** 핸들러 함수를 컴포넌트 상단(또는 커스텀 훅 내부)에 별도로 선언(`handleFolderInputKeyDown` 등)하여 참조하는 방식으로 변경해야 합니다.

## 2. 백엔드 (`parantier-api`)

도메인 주도 설계를 적용하려는 노력은 좋으나, 응용 서비스 계층과 도메인 모델 내부에서 몇 가지 안티 패턴이 보입니다.

### 🚩 문제점 & 개선 방안

1. **단일 책임 원칙(SRP) 위배를 피하는 메서드 분리**
   * **현황:** `TaskPostService.java`의 `savePost()` 메서드는 ID의 null 여부에 따라 **생성(Create)**과 **수정(Update)**을 동시에 처리하고 있습니다. 또한 수정 시 기존 블록을 무조건 지우고 새로 생성(`deleteByPostId` -> `insert`)하는 거친(Blunt) 방식을 사용합니다.
   * **개선:** `createPost()`와 `updatePost()`로 메서드를 명확히 분리해야 합니다. 비즈니스 로직상 생성과 수정은 발생 조건과 검증 로직이 다르기 때문입니다. 블록(TaskBlock) 관리도 단순히 지우고 덮어쓰기보다는 식별 가능한 방법으로 업데이트하는 것이 안전합니다.

2. **도메인 엔티티 내 불변성과 가변성의 혼재**
   * **현황:** `User.java` 도메인을 보면 상태를 직접 수정하는 메서드(`this.isActive = false`)와 빌더를 통해 아예 새로운 객체를 반환하는 메서드(`withUsername()`) 패턴이 혼재되어 있습니다. 특히 `with...` 메서드에서 Lombok Builder의 보일러플레이트 코드가 반복됩니다.
   * **개선:** `@Builder(toBuilder = true)`를 사용하여 `with...` 내부의 중복된 빌더 코드를 줄이거나, 엔티티의 상태 변경 패턴을 가변(Mutable - JPA 환경에서 흔함) 또는 불변(Immutable) 중 **하나의 스타일로 통일**하는 것이 덜 혼란스럽습니다.

3. **주석 처리된 절차지향적 서비스 코드**
   * **현황:** `AuthService.java` 등을 보면 `// 1. 이메일 중복 체크`, `// 2. 비밀번호 검증` 형태로 책 읽듯이 절차적으로 긴 코드가 이어집니다.
   * **개선:** 주석이 필요할 정도로 로직의 단계가 길다면, 해당 코드 블럭 자체를 `validateEmail()`, `verifyPassword()` 같은 명확한 이름의 **프라이빗 메서드(Private Method)로 추출**하여 코드 자체가 주석을 대신하도록(Self-documenting) 만드는 것이 클린 코드의 핵심입니다.
