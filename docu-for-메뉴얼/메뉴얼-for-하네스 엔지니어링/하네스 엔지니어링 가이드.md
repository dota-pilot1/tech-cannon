# 하네스 엔지니어링 (Harness Engineering) 가이드

> Claude 같은 AI 코딩 어시스턴트를 **효율적으로 활용하는 방법론**의 통칭.
> Anthropic 공식 용어는 아니며, 커뮤니티에서 베스트 프랙티스를 묶어 부르는 이름.

---

## 1. 핵심 원리

> **Claude에게 "모든 것"을 주지 말고, "필요한 것"만 주어라.**

Claude는 매 대화마다 컨텍스트 윈도우(처리 가능한 토큰 한도)가 있음.
여기에 관련 없는 정보가 많을수록:
- 중요한 규칙을 놓침
- 판단력이 흐려짐
- 토큰 낭비 → 응답 속도 저하

```
parantier-api/
└── CLAUDE.md    ← 백엔드 작업 시 자동 로드 (DDD 규칙 등)

parantier-front/
└── CLAUDE.md    ← 프론트 작업 시 자동 로드 (라우팅 규칙 등)
```

## 3. CLAUDE.md 작성 원칙

### ✅ 넣어야 할 것

| 항목 | 예시 |
|------|------|
| 절대 규칙 (변하지 않음) | 서버 직접 시작 금지, 특정 패키지 사용 금지 |
| 왜(Why) 설명 | "@Data 금지" + "setter가 생겨 불변성 깨짐" |
| 하위 문서 참조 링크 | 상세 내용은 docs/architecture.md 참고 |
| 자주 실수하는 패턴 | API 경로 /api 중복 금지 등 |

### ❌ 넣으면 안 되는 것

| 항목 | 이유 |
|------|------|
| 자주 바뀌는 정보 (API 명세 등) | 금방 outdated됨 |
| 긴 코드 예시 | 토큰 낭비, 실제 코드 보는 게 더 정확 |
| "항상 ~해라" 남발 | Claude 판단력 저하 |
| 민감 정보 (비밀번호, 키 등) | 보안 위험 ⚠️ |

### 명령보다 의도를 써라

```
❌ 나쁜 예:
"새 파일 만들 때 항상 Builder 패턴 사용해라"

✅ 좋은 예:
"이 프로젝트는 도메인 객체 불변성을 위해 @Getter+@Builder 사용.
 @Data/@Setter는 setter가 생겨 외부에서 값을 마음대로 변경할 수 있어 금지."
```

**왜인지 알면 Claude가 예외 상황도 스스로 판단한다.**

### 중요도 구분

```markdown
# IMPORTANT  ← Claude가 반드시 지켜야 할 것
- 서버를 절대 직접 시작하지 말 것
- 모든 코드는 com.mapo.palantier 하위에

# REFERENCE  ← 참고용 (필요할 때만)
- 프로젝트 배경 설명...
```

## 4. 작업 단위 쪼개기 (Context Window 관리)

긴 작업을 한 대화에서 다 하려 하면 Claude가 앞 내용을 잊기 시작함.

```
❌ 한 대화에서 모두:
"task 레이어 분리하고, wiki도 하고, @Data도 제거하고, CLAUDE.md도 분리해줘"

✅ 대화를 나눠서:
대화 1: task/wiki 레이어 분리
대화 2: @Data 제거
대화 3: CLAUDE.md 분리
```

**특히 파일 수가 많아지는 리팩토링은 도메인 단위로 한 대화씩.**

## 5. 컨텍스트를 직접 주는 방법

Claude가 파악하지 못할 것 같은 배경은 대화 시작에 명시적으로 제공.

```
✅ 좋은 방법:
"지금 task 도메인 리팩토링 중이야.
 현재 Service가 Mapper를 직접 주입하고 있어서 DIP 위반인 상태.
 Repository 인터페이스 패턴으로 바꾸려고 해."

❌ 나쁜 방법:
"task 도메인 고쳐줘"
```

## 9. DDD 기본 원칙 (백엔드)

> Domain-Driven Design — 비즈니스 도메인 중심으로 코드를 구조화하는 설계 방법론

### 핵심 개념

**도메인이 중심이다.** DB 구조나 프레임워크가 아닌, 비즈니스 개념이 코드 구조를 결정한다.

### 4계층 구조

```
presentation     Controller, Request/Response DTO
     ↓
application      Service (비즈니스 흐름 조율)
     ↓
domain           도메인 객체, Repository 인터페이스   ← 핵심
     ↑
infrastructure   Mapper(@Mapper), RepositoryImpl
```

### 핵심 규칙 3가지

**1. 의존성 역전 (DIP)**
- Service는 Repository **인터페이스**만 알고 있음
- 실제 DB 기술(MyBatis)은 infrastructure 안에 숨김
- → DB를 JPA로 바꿔도 Service 코드는 건드리지 않아도 됨

**2. 도메인 객체 불변성**
- `@Data`/`@Setter` 금지 → `@Getter` + `@Builder`만 사용
- 상태 변경은 도메인 메서드로만 (`user.deactivate()`, `folder.withUpdated()`)
- → "어디서 값이 바뀌었는지" 추적 가능

**3. 풍부한 도메인 모델 (Rich Domain Model)**
- 도메인 객체가 데이터만 담는 POJO가 아니라 **비즈니스 로직도 포함**
- 팩토리 메서드: `User.createNewUser(email, password, username)`
- 상태 메서드: `user.isAdmin()`, `org.isRootOrganization()`

### 이 프로젝트 적용 현황

```
com.mapo.palantier.{domain}/
├── domain/          ← 도메인 객체 + Repository 인터페이스  ✅
├── infrastructure/  ← Mapper + RepositoryImpl             ✅
├── application/     ← Service                             ✅
└── presentation/    ← Controller + dto/                   ✅
```

## 10. FSD 기본 원칙 (프론트엔드)

> Feature-Sliced Design — 프론트엔드 코드를 기능/도메인 단위로 구조화하는 아키텍처 방법론

### 핵심 개념

**레이어 → 슬라이스 → 세그먼트** 3단계로 코드를 분류한다.

### 레이어 구조 (이 프로젝트)

```
src/
├── app/        앱 초기화, 라우터, 전역 Provider
├── pages/      라우트 단위 페이지 (조합만, 자체 로직 없음)
├── features/   기능 단위 (hooks, components, api)
├── entities/   도메인 단위 (api, types, model/store)
└── shared/     순수 공통 (ui, hooks, lib, axios)
```

### 의존성 방향 (단방향, 절대 역방향 금지)

```
pages → features → entities → shared
```

### 각 레이어의 역할

| 레이어 | 역할 | 예시 |
|--------|------|------|
| `shared` | 도메인 무관한 순수 공통 요소 | Button, useConfirm, axios |
| `entities` | 도메인 데이터 + API + 전역 상태 | workApi.ts, authStore.ts |
| `features` | 특정 기능의 비즈니스 로직 | useWorks.ts, WorkChatPanel.tsx |
| `pages` | 라우트 단위 조합 컴포넌트 | WorkPage.tsx, IssuePage.tsx |

### 핵심 규칙

**1. 같은 레이어끼리 cross-import 금지**
```typescript
// ❌ features/work에서 features/issue import
import { useIssues } from '@/features/issue/hooks/useIssues'

// ✅ entities에서 가져와야 함
import { issueApi } from '@/entities/issue/api/issueApi'
```

**2. 하위 레이어가 상위 레이어 import 금지**
```typescript
// ❌ entities에서 features import
// ❌ shared에서 entities import
```

**3. pages는 조합만, 로직은 features/entities로**
```typescript
// ❌ Page에서 직접 API 호출
const { data } = useQuery({ queryFn: () => workApi.getAll() })

// ✅ features hook에 위임
const { works } = useWorks()
```

### 이 프로젝트 적용 현황

```
entities/work/api/workApi.ts          ← API 함수
entities/work/types/work.ts           ← 타입 정의
entities/user/model/authStore.ts      ← 전역 상태 (zustand)
features/work/hooks/useWorks.ts       ← TanStack Query 훅
features/work/components/WorkChatPanel.tsx  ← 기능 컴포넌트
pages/work/WorkPage.tsx               ← 페이지 조합
shared/ui/button.tsx                  ← 공통 UI
shared/hooks/useConfirm.tsx           ← 공통 훅
```

## 11. DDD × FSD 연결 구조

백엔드 DDD와 프론트엔드 FSD는 **도메인 단위**라는 공통 언어로 연결된다.

```
백엔드 (DDD)                    프론트엔드 (FSD)
─────────────────               ──────────────────────────
work/domain/Work.java      ↔    entities/work/types/work.ts
work/application/WorkService ↔  features/work/hooks/useWorks.ts
work/presentation/Controller ↔  entities/work/api/workApi.ts
                                pages/work/WorkPage.tsx
```

같은 도메인명(`work`, `issue`, `user`)을 백/프론트에서 일관되게 사용하므로
어느 레이어를 보더라도 어떤 도메인인지 바로 파악 가능하다.
