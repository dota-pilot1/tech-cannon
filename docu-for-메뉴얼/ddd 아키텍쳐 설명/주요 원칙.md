# DDD(도메인 주도 설계) 주요 원칙

> 이 문서는 `mapo-palantier-project`에 적용된 DDD 원칙을 **현재 실제 코드 기준**으로 정리한 가이드입니다.
> 마지막 업데이트: `task`, `wiki` 도메인 DDD 리팩토링 완료 이후

## 1. 레이어드 아키텍처 (Layered Architecture)

> **"각 레이어는 명확한 책임을 가지며, 의존 방향은 항상 단방향이어야 한다."**

```
presentation   →   application   →   domain   ←   infrastructure
(Controller)       (Service)         (Entity,       (Mapper,
                                     Repository     RepositoryImpl)
                                     인터페이스)
```

| 레이어 | 역할 | 예시 (task 도메인) |
|--------|------|------------------|
| **Presentation** | HTTP 요청/응답 처리, DTO 수신 | `TaskPostController.java` |
| **Application** | 비즈니스 흐름 조율, 트랜잭션 관리 | `TaskPostService.java` |
| **Domain** | 핵심 비즈니스 로직, Repository 인터페이스 | `TaskPost.java`, `TaskPostRepository.java` |
| **Infrastructure** | DB 접근 구현 (MyBatis Mapper + RepositoryImpl) | `TaskPostMapper.java`, `TaskPostRepositoryImpl.java` |

### ✅ 현재 프로젝트의 실제 구조 (`task` 도메인)

```
task/
├── application/
│   ├── TaskPostService.java
│   ├── TaskFolderService.java
│   └── TaskCommentService.java
├── domain/
│   ├── TaskPost.java              (@Getter @Builder + 팩토리 메서드)
│   ├── TaskBlock.java             (@Getter @Builder)
│   ├── TaskFolder.java            (@Getter @Builder + 팩토리 메서드)
│   ├── TaskComment.java           (@Getter @Builder + 팩토리 메서드)
│   ├── BlockType.java             (Enum Value Object)
│   ├── TaskPostRepository.java    (인터페이스)
│   ├── TaskBlockRepository.java   (인터페이스)
│   ├── TaskFolderRepository.java  (인터페이스)
│   └── TaskCommentRepository.java (인터페이스)
├── infrastructure/
│   ├── TaskPostMapper.java        (@Mapper - MyBatis)
│   ├── TaskPostRepositoryImpl.java
│   ├── TaskBlockMapper.java
│   ├── TaskBlockRepositoryImpl.java
│   ├── TaskFolderMapper.java
│   ├── TaskFolderRepositoryImpl.java
│   ├── TaskCommentMapper.java
│   └── TaskCommentRepositoryImpl.java
└── presentation/
    ├── TaskPostController.java
    ├── TaskFolderController.java
    ├── TaskCommentController.java
    └── dto/
        ├── TaskPostRequest.java
        ├── TaskBlockRequest.java
        ├── TaskFolderRequest.java
        └── TaskCommentRequest.java
```

`wiki` 도메인도 동일한 4계층 구조로 구성되어 있습니다.

## 2. 의존성 역전 원칙 (DIP — Dependency Inversion Principle)

> **"상위 레이어는 하위 레이어의 구체적인 구현에 의존하면 안 된다."**

- `Application(Service)` 레이어는 `Infrastructure(Mapper)`를 직접 알아서는 안 됩니다.
- `Domain` 레이어에 **Repository 인터페이스**를 선언하고, `Infrastructure` 레이어에서 이를 **구현**합니다.
- `Service`는 인터페이스만 바라보므로, DB 기술이 바뀌어도 Service 코드를 수정할 필요가 없습니다.

### ✅ 현재 코드 — DIP 준수

**domain 레이어: 인터페이스 선언**
```java
// task/domain/TaskPostRepository.java
public interface TaskPostRepository {
    List<TaskPost> findAll();
    List<TaskPost> findByFolderId(Long folderId);
    Optional<TaskPost> findById(Long id);
    Optional<TaskPost> findByIdWithBlocks(Long id);
    void insert(TaskPost post);
    void update(TaskPost post);
    void softDelete(Long id);
}
```

**infrastructure 레이어: 인터페이스 구현**
```java
// task/infrastructure/TaskPostRepositoryImpl.java
@Repository
@RequiredArgsConstructor
public class TaskPostRepositoryImpl implements TaskPostRepository {
    private final TaskPostMapper taskPostMapper; // Mapper는 여기서만 사용

    @Override
    public List<TaskPost> findAll() { return taskPostMapper.findAll(); }
    // ... 나머지 구현
}
```

**application 레이어: 인터페이스에만 의존**
```java
// task/application/TaskPostService.java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class TaskPostService {
    private final TaskPostRepository taskPostRepository;   // ✅ 인터페이스만 참조
    private final TaskBlockRepository taskBlockRepository; // ✅ Mapper 직접 주입 없음
}
```

## 3. 풍부한 도메인 모델 (Rich Domain Model)

> **"도메인 객체는 데이터를 담는 그릇이 아니라, 비즈니스 로직을 스스로 갖는 존재여야 한다."**

도메인 로직이 Service에 집중되는 **빈약한 도메인 모델(Anemic Domain Model)** 을 피하고,
도메인 객체 안에 **팩토리 메서드, 상태 변경 메서드**를 둡니다.

### ✅ 현재 코드 — 팩토리 메서드 패턴 적용

**TaskPost — 생성/수정 팩토리 메서드**
```java
// task/domain/TaskPost.java
@Getter
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class TaskPost {
    private Long id;
    private Long folderId;
    private String title;
    private Long authorId;
    private String authorName;   // ⚠️ 조회용 필드 (아래 Bounded Context 섹션 참고)
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
    private LocalDateTime deletedAt;
    private List<TaskBlock> blocks; // 상세 조회 시에만 포함

    // 신규 생성 — new TaskPost() + setter 대신 의도가 명확한 팩토리 메서드
    public static TaskPost create(Long folderId, String title, Long authorId) {
        return TaskPost.builder()
                .folderId(folderId).title(title).authorId(authorId).build();
    }

    // 수정 — 어떤 필드가 변경되는지 명시적으로 표현
    public static TaskPost modify(Long id, Long folderId, String title, Long authorId) {
        return TaskPost.builder()
                .id(id).folderId(folderId).title(title).authorId(authorId).build();
    }
}
```

**TaskFolder — withUpdated 패턴 (불변 수정)**
```java
// task/domain/TaskFolder.java
public static TaskFolder create(Long parentId, String name, Integer sortOrder, Long createdBy) {
    return TaskFolder.builder()
            .parentId(parentId).name(name)
            .sortOrder(sortOrder != null ? sortOrder : 0)
            .createdBy(createdBy).build();
}

// 수정 시 새 인스턴스를 반환하여 불변성 유지
public TaskFolder withUpdated(String name, Long parentId, Integer sortOrder) {
    return TaskFolder.builder()
            .id(this.id)
            .parentId(parentId != null ? parentId : this.parentId)
            .name(name)
            .sortOrder(sortOrder != null ? sortOrder : this.sortOrder)
            .createdBy(this.createdBy)
            .createdAt(this.createdAt).build();
}
```

**Service에서의 사용 — new + setter 없이 팩토리 메서드로 생성**
```java
// task/application/TaskFolderService.java
@Transactional
public Long createFolder(TaskFolderRequest request, Long currentUserId) {
    TaskFolder folder = TaskFolder.create(       // ✅ 팩토리 메서드 사용
            request.getParentId(),
            request.getName(),
            request.getSortOrder(),
            currentUserId
    );
    taskFolderRepository.insert(folder);
    return folder.getId();
}

@Transactional
public void updateFolder(Long id, TaskFolderRequest request) {
    TaskFolder existing = getFolderById(id);
    TaskFolder updated = existing.withUpdated(   // ✅ 불변 수정 패턴
            request.getName(),
            request.getParentId(),
            request.getSortOrder()
    );
    taskFolderRepository.update(updated);
}
```

## 4. 불변성 (Immutability)

> **"도메인 객체의 상태는 외부에서 자유롭게 바꿀 수 없어야 한다."**

- `@Data`, `@Setter` 사용을 금지합니다.
- `@Getter` + `@Builder`를 기본으로 사용합니다.
- 상태 변경이 필요할 때는 **팩토리 메서드 또는 `withXxx()` 메서드**를 통해 새 인스턴스를 반환합니다.

### 현재 프로젝트의 도메인 어노테이션 기준

| 어노테이션 | 사용 여부 | 이유 |
|-----------|----------|------|
| `@Getter` | ✅ 허용 | 읽기 전용 접근 |
| `@Builder` | ✅ 허용 | 생성자 대신 명시적 빌더 |
| `@NoArgsConstructor` | ✅ 허용 | MyBatis ResultMap 역직렬화에 필요 |
| `@AllArgsConstructor` | ✅ 허용 | `@Builder`와 함께 사용 시 필요 |
| `@Setter` | ❌ 금지 | 외부에서 필드 직접 변경 가능 → 불변성 파괴 |
| `@Data` | ❌ 금지 | `@Setter` 포함, 불변성 파괴 |

## 5. Bounded Context (경계가 있는 컨텍스트)

> **"각 도메인은 명확한 경계를 가지며, 다른 도메인의 내부 구현을 알아서는 안 된다."**

이 프로젝트에서는 **최상위 패키지** (`user`, `task`, `wiki`, `meeting`, `workspace` 등)가 각각의 Bounded Context를 담당합니다.

### ⚠️ 현재 남아있는 경계 침투 — 개선 검토 필요

```java
// task/domain/TaskPost.java
private String authorName;   // ← user 컨텍스트의 데이터가 task 도메인 객체 안에 존재

// task/domain/TaskComment.java
private String authorName;   // ← 동일한 문제

// wiki/domain/WikiPost.java
private String authorName;   // ← 동일한 문제
```

현재는 MyBatis JOIN 조회 결과를 도메인 객체에 직접 매핑하기 위해 `authorName` 필드를 보유하고 있습니다.
이는 실용적인 이유로 허용된 트레이드오프이며, 추후 아래 방향으로 개선할 수 있습니다.

```java
// 개선 방향 — 도메인 객체는 ID 참조만 보유
// task/domain/TaskPost.java
private Long authorId;  // ✅ ID만 보유

// 조회용 응답은 별도 Response DTO에서 처리
// task/presentation/dto/TaskPostResponse.java
public class TaskPostResponse {
    private Long id;
    private String title;
    private String authorName;  // ✅ 조회 결과는 DTO에서 담당
}
```

## 6. Repository 패턴

> **"도메인 객체의 영속성 처리는 Repository가 전담하며, 도메인은 DB 기술을 알지 못한다."**

### 현재 프로젝트 전체 Repository 적용 현황

| 도메인 | Repository 인터페이스 (domain) | RepositoryImpl (infrastructure) | 상태 |
|--------|-------------------------------|--------------------------------|------|
| `user` | ✅ | ✅ | ✅ 완료 |
| `authority` | ✅ | ✅ | ✅ 완료 |
| `workspace` | ✅ | ✅ | ✅ 완료 |
| `meeting` | ✅ | ✅ | ✅ 완료 |
| `task` | ✅ | ✅ | ✅ 완료 |
| `wiki` | ✅ | ✅ | ✅ 완료 |

모든 도메인에서 Repository 패턴이 완료된 상태입니다.

### Repository 패턴 구조 요약

```
domain/TaskPostRepository.java          ← 인터페이스 (domain 레이어)
infrastructure/TaskPostMapper.java      ← MyBatis @Mapper (실제 SQL)
infrastructure/TaskPostRepositoryImpl   ← 인터페이스 구현체, Mapper 위임
application/TaskPostService.java        ← Repository 인터페이스만 의존
```

## 7. Value Object (값 객체)

> **"식별자가 없고, 값 자체가 의미를 갖는 개념은 Value Object로 모델링한다."**

- 원시 타입(String, int 등)으로 표현하던 개념을 별도 클래스/enum으로 분리합니다.
- Value Object는 **불변**이며, 동등성은 **값으로 비교**합니다.

### ✅ 현재 적용된 Enum Value Object

```java
// task/domain/BlockType.java
public enum BlockType {
    NOTE,     // 마크다운 텍스트
    MMD,      // Mermaid 다이어그램
    FIGMA,    // Figma 임베드 URL
    FILE,     // 파일 첨부 (JSON)
    DBTABLE   // DB 테이블 정의 (JSON)
}

// wiki/domain/WikiBlockType.java — task와 별도 관리 (Bounded Context 분리)
public enum WikiBlockType { ... }

// workspace 도메인
public enum NodeType { ... }
public enum NodeStatus { ... }
public enum NodePriority { ... }
```

### ⚠️ 개선 검토 — String 원시 타입으로 남아있는 개념

```java
// wiki/domain/WikiPost.java
private String tags; // "컨벤션,TypeScript,필독" — 콤마 구분 문자열

// 개선 방향: Tags Value Object
public class Tags {
    private final List<String> values;

    public static Tags from(String csv) {
        return new Tags(Arrays.asList(csv.split(",")));
    }
    public String toCsv() { return String.join(",", values); }
}
```

## 8. 예외 처리 원칙

> **"예외는 도메인의 언어로 표현되어야 한다."**

- `IllegalArgumentException` 같은 일반 예외 대신, **도메인 전용 예외**를 사용합니다.
- `common/exception/` 하위에 도메인 예외를 모아 중앙 관리합니다.
- `GlobalExceptionHandler`로 전역에서 일관된 에러 응답을 반환합니다.

### 현재 예외 구조

```
common/exception/
├── ErrorCode.java               (에러 코드 Enum 중앙 관리)
├── GlobalExceptionHandler.java  (전역 예외 처리)
├── UserNotFoundException.java
├── DuplicateEmailException.java
└── ...
```

### ⚠️ 현재 일부 도메인에서 일반 예외 직접 사용 중

```java
// task/application/TaskPostService.java — 현재 코드
.orElseThrow(() -> new IllegalArgumentException("게시글을 찾을 수 없습니다: " + id));

// task/application/TaskFolderService.java — 현재 코드
.orElseThrow(() -> new IllegalArgumentException("폴더를 찾을 수 없습니다: " + id));
```

```java
// 개선 방향 — 도메인 전용 예외 사용
.orElseThrow(() -> new TaskPostNotFoundException(ErrorCode.POST_NOT_FOUND));
```

## 9. DTO 경계 원칙

> **"도메인 객체를 외부에 직접 노출하지 않는다."**

- **Request DTO**: 클라이언트 → Controller → Service 로 전달되는 입력값
- 도메인 객체(`TaskPost`, `WikiPost` 등)를 Controller에서 직접 반환하고 있으며, 추후 Response DTO 분리를 검토합니다.

### 현재 DTO 구조

```
task/presentation/dto/
├── TaskPostRequest.java     ← 게시글 생성/수정 입력값
├── TaskBlockRequest.java    ← 블록 데이터 입력값
├── TaskFolderRequest.java   ← 폴더 생성/수정 입력값
└── TaskCommentRequest.java  ← 댓글 생성 입력값

wiki/presentation/dto/
├── WikiPostRequest.java
├── WikiBlockRequest.java
└── WikiFolderRequest.java
```

### ⚠️ 현재 Controller가 도메인 객체를 직접 반환 중

```java
// task/presentation/TaskPostController.java — 현재 코드
public ResponseEntity<TaskPost> getPost(@PathVariable Long id) {
    return ResponseEntity.ok(taskPostService.getPostWithBlocks(id)); // 도메인 객체 직접 반환
}

// 개선 방향
public ResponseEntity<TaskPostResponse> getPost(@PathVariable Long id) {
    TaskPost post = taskPostService.getPostWithBlocks(id);
    return ResponseEntity.ok(TaskPostResponse.from(post)); // DTO 변환 후 반환
}
```

## 10. 현재 상태 종합 평가표

| # | 원칙 | 현재 상태 | 비고 |
|---|------|----------|------|
| 1 | 레이어드 아키텍처 | ✅ 완료 | 전 도메인 4계층 분리 완료 |
| 2 | 의존성 역전 (DIP) | ✅ 완료 | 전 도메인 Repository 인터페이스 도입 완료 |
| 3 | Rich Domain Model | ✅ 완료 | 팩토리 메서드, `withXxx()` 패턴 적용 |
| 4 | 불변성 | ✅ 완료 | `@Getter` + `@Builder`, `@Data`/`@Setter` 미사용 |
| 5 | Bounded Context | ⚠️ 부분 | `authorName` 필드가 도메인 객체에 잔존 |
| 6 | Repository 패턴 | ✅ 완료 | 전 도메인 인터페이스 + 구현체 분리 완료 |
| 7 | Value Object | ⚠️ 부분 | Enum VO는 완료, `WikiPost.tags` String 잔존 |
| 8 | 도메인 예외 | ⚠️ 부분 | 일부 Service에서 `IllegalArgumentException` 직접 사용 |
| 9 | DTO 경계 | ⚠️ 부분 | Request DTO 분리 완료, Response DTO 미분리 |

### 남은 개선 우선순위

| 우선순위 | 작업 |
|---------|------|
| 🟡 중간 | `task`, `wiki` Service의 `IllegalArgumentException` → 도메인 전용 예외로 교체 |
| 🟡 중간 | Controller의 도메인 객체 직접 반환 → `TaskPostResponse`, `WikiPostResponse` DTO 분리 |
| 🟢 낮음 | `authorName` 필드를 도메인 객체에서 제거하고 Response DTO로 이동 |
| 🟢 낮음 | `WikiPost.tags` → `Tags` Value Object 도입 |
